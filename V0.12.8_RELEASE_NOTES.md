# FLIM Studio 0.12.8

## Fixed: global training silently ignored every training image after the first

Reported as: training a tri-exponential global model across 3 images,
each independently verified (by phasor position, on the universal
semicircle) to be a clean single-species mono-exponential decay at a
different lifetime, failed to recover the 3 expected component
lifetimes.

### Root cause

Found in `native/flimfit_labview.c`'s `flim_train_global_model_v1`: the
`maxGlobalPixels` cap (this app's sidebar "Max pixels", default `20,000`)
is enforced by iterating pixels in `(image, row, column)` order and
simply refusing any further pixel once the cap is hit:

```c
if (maxGlobalPixels > 0 && selectedCount >= maxGlobalPixels) {
    fitStatusMap[p] = -7.0;
    continue;
}
```

A single 512×512 acquisition is already 262,144 pixels — over 13× the
default cap. With more than one training image, this silently means
**only the first training image (or part of it) ever contributes a
single pixel to the fit; every later image is entirely excluded**
(`fit_status == -7` for the whole thing), with no error or warning
anywhere. A "shared taus across 3 images" training run was, in practice,
training on one image's single species — which a coordinate-descent
optimizer starting from generic seed lifetimes has no way to turn into 3
correctly-separated components, since it never sees the other two
species' data at all.

This affects essentially any real multi-image training run, not just
this specific 3-mono-exponential test case — the DLL itself isn't
rebuilt here (no C toolchain available in this environment to safely
verify a change to compiled, GPL-linked native code); instead:

### The fix

`train_global_model()` (`flim_app/processing.py`) now pre-subsamples
each training image's own pixel *mask* down to a fair per-image share
(`max_global_pixels ÷ image_count`, via a fixed-seed random draw of
pixel coordinates) **before** the DLL ever sees it, whenever there's more
than one training image and that per-image share is smaller than the
image itself. The DLL's own `maxGlobalPixels` truncation still runs
afterward as before, but the pool it sees is now already balanced across
every training image, so it accepts (almost) all of it rather than
draining the whole budget on whichever image happens to come first in
the table.

### New: per-image pixel counts, visible in the Training dialog

A new **"Px used/total"** column in the training-image table, filled in
once training completes — the direct way to confirm the fix worked (or
to catch this class of problem again if it recurs): every row should now
show a non-trivial fraction, not zero for every image but the first.

### What to do with a model trained before this fix

**Retrain it** — the same "re-add the same images, click Train again"
steps as 0.12.7 (which fixed a related but separate `dt_ns` provenance
bug in the same training path). Check the new "Px used/total" column
this time to directly confirm all 3 images contributed pixels before
trusting the result.

### If it's still not separating your 3 lifetimes after this

The per-image mask fix addresses the most likely cause given the exact
symptom described, but two other levers are worth trying, both already
in the sidebar under NATIVE FLIMLIB FIT:
- **Initial τ values (ns, comma separated)** — set explicit starting
  guesses near your 3 known (phasor-verified) lifetimes, e.g. `1, 2.5, 4`.
  The DLL's own fallback seeding (used when this is left blank) picks
  fixed fractions of the acquisition window (`0.35×`, `0.175×`, `0.117×`
  of the total time range) regardless of your actual data — a poor
  starting point pushes any nonlinear optimizer, coordinate-descent
  especially, toward a local minimum rather than the true 3-component
  solution.
- **Global iterations** — capped at `20` by `AnalysisSettings.normalized()`
  (a pre-existing limit, unchanged here). If 20 iterations from a good
  initial guess still doesn't separate 3 clearly-distinct species, that
  would point at something beyond what's fixable from the Python side —
  worth reporting back with the resulting τ values and the new "Px
  used/total" numbers if so.
