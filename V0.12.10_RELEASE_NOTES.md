# FLIM Studio 0.12.10

## Global training's pixel sample now respects the minimum-count threshold

Follow-up to 0.12.8/0.12.9's global-training pixel-budget fixes, from a
good suggestion: use thresholding to shrink the effective pixel pool,
rather than only ever spending the budget on raw, unfiltered pixels.

Previously, 0.12.8's per-image fair-share subsampling drew its random
sample from *every* pixel position in each training image, background
included. Any pixel below **Fit/native min total counts**
(`cfg.fit_min_counts`, the exact same value already sent to the DLL as
`minPhotons`) would just get rejected by the DLL a step later anyway
(`fit_status == -2`) — meaning a real chunk of an already-scarce budget
could be spent on pixels that were never going to contribute to the fit,
especially for images that are mostly background around a smaller
foreground region.

`train_global_model()` (`flim_app/processing.py`) now computes each
image's photon-count-eligible pixels first (`decay_stack.sum(axis=-1) >=
cfg.fit_min_counts` — the same computation, same threshold, as the
DLL's own check) and draws the per-image random sample from *that* set
instead of the raw pixel grid. If an image's number of eligible pixels
is already at or under its fair-share budget, every eligible pixel is
used outright rather than randomly sampling a subset of them. This is
the same thresholding-as-masking approach `analyze_dataset()` already
uses for the single-image **FLIMLib — global shared τ** method's own
`native_mask` — training's mask simply never had it applied before.

Practically: a stricter minimum-count threshold now does double duty —
it always excluded dim pixels from the fit itself, and now it *also*
shrinks the effective competition for a limited pixel budget, so a
modest **Max pixels** cap goes much further toward covering every
relevant (foreground) pixel from every training image, without
necessarily needing 0.12.9's `0 = no cap` at all.

## Aside: why not just make the underlying fit algorithm faster?

Worth being direct about this, since it came up: the reason this project
needs a pixel cap at all — where an established tool like TRI2 can
apparently work with full datasets more comfortably — very likely comes
down to the underlying optimization algorithm, not something fixable by
adjusting a cap. `native/flimfit_labview.c`'s global solver is a
coordinate-descent search with a shrinking step size, re-scoring the
*entire* selected pixel pool on every trial of the shared τ values.
Established global-analysis tools for TCSPC (TRI2 among them) typically
use variable projection (VARPRO): for any fixed set of shared τ values,
each pixel's linear amplitude/background parameters have a closed-form
least-squares solution, so the nonlinear search only ever has to explore
the 2-3 actual τ values, using real gradient information (e.g.
Levenberg-Marquardt) instead of a coordinate-by-coordinate grid search —
typically converging in far fewer, far cheaper steps. Closing that gap
for real would mean reimplementing the core fitting algorithm in the
compiled, GPL-linked native DLL — a substantially bigger and riskier
undertaking than this project's Python-side fixes, and not something to
attempt without a C toolchain and a real way to numerically verify the
result (neither available in this environment). The threshold-based
masking above is the practical, safe mitigation available without
touching that code.
