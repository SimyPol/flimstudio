# FLIM Studio 0.12.7

## Fixed: global-model training used the main window's Time-bin width, not the training images' own

A real correctness bug, reported as: after training and switching to
Application mode, **Time-bin width**/**Native bin width** showed
`0.1953125` ns where ~0.4 ns was expected.

Root cause: `train_global_model()` built its `AnalysisSettings` via
`settings.normalized(items[0].dataset.time_bins)`, where `settings` came
from the *main window's current sidebar state* at the moment **Train**
was clicked — **not** from the training images actually added to the
dialog. Each training image's own, correct `dt_ns` (read from its own
file) was loaded and used for the fit itself, but never checked against —
or used to set — the model's recorded `dt_ns`/`native_bin_width_ns`.
Whatever the main window's **Time-bin width** field happened to show
(reflecting whichever *other* dataset was last loaded there, or nothing
in particular) got silently baked into the trained model instead. Since
`native_bin_width_ns` is applied verbatim at fit time (converts bin index
→ real time in the native DLL call), any mismatch here silently scales
*every* fitted lifetime by the ratio between the two — the same class of
bug fixed for the sidebar's manual entry in 0.12.5, just reachable through
training instead.

(As an aside: `0.1953125` ns is also, by design, the exact hardcoded
`dt_ns` FLIM Studio's own bundled **Demo data** dataset uses internally
[`flim_app/demo.py`] — if the demo dataset, or a training image sharing
its timing, was involved anywhere in the chain, that specific number is
expected for *that* data. The bug above is about where the value came
from, not that 0.1953125 is inherently wrong for every dataset.)

### The fix

`train_global_model()` (`flim_app/processing.py`) now:
1. Reads `dt_ns` from the training images themselves — specifically,
   requires every added training image to share the same `dt_ns`,
   raising a clear error naming the mismatched file if they don't (this
   was previously never checked at all).
2. Uses that confirmed-consistent value for the model's `dt_ns`, and
   (via `AnalysisSettings.normalized()`'s existing `<=0`-means-auto
   fallback) for `native_bin_width_ns` too, when the sidebar's Native bin
   width mode is Auto — done via a `dataclasses.replace()`d copy of
   `settings` before normalizing, so the correction is in place before
   `native_bin_width_ns`'s own auto-fallback resolves, not after.

The main window's Time-bin width field is no longer consulted for
training at all; it has no necessary connection to whatever's in the
Training dialog's table.

### What to do with a model trained before this fix

**Retrain it.** Reopen the Training dialog, re-add the same images (a
shared IRF/background, if you had one set, still applies to all of them
at once — see 0.12.6's multi-select), and click **Train** again. The
newly trained model will carry the correct `dt_ns`/`native_bin_width_ns`
this time. If you already ran **Application mode** with the old model,
treat any fitted lifetimes from that run as suspect until re-checked
against a retrained model — the scale error compounds directly into every
reported τ.

### Status

Implemented and reviewed via careful manual code tracing (no Python
interpreter available in this environment to run it — see `BUILDING.md`'s
existing caveat). Please retrain a model from your real acquisitions and
confirm the sidebar's **Native bin width** summary (after **Use this
model now**) now shows the value you actually expect for those files, not
0.1953125 (unless that genuinely is your data's real bin width).
