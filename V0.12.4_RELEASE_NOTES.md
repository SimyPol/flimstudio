# FLIM Studio 0.12.4

## Parallel per-pixel native reconvolution fitting

A new sidebar field under NATIVE FLIMLIB FIT, **Reconvolution fit worker
processes** (default `1`, unchanged behaviour), splits the image into that
many row-band chunks and fits each chunk in its own disposable subprocess
concurrently -- real wall-clock speedup, up to roughly your core count,
for the "FLIMLib — reconvolution" method specifically.

### Why not threads, and why this is safe

The per-pixel fit already goes through the native DLL as one call passing
the whole image at once, serialized by `_DLL_LOCK` -- almost certainly
there because the underlying FLIMLib C code was never verified reentrant.
Removing that lock to let Python threads call into *one* loaded DLL
instance concurrently would be a real gamble with a pipeline this app
validates against LabVIEW to sub-0.1 ns precision.

Multiple *subprocesses* sidestep that entirely: each chunk gets its own OS
process with its own independent DLL load, so there's no shared state
between them for `_DLL_LOCK`'s concern to even apply to. This reuses the
crash-isolation architecture `native_worker.py` already provides for a
single fit, just fanned out. A `ThreadPoolExecutor` drives the fan-out
(not more subprocesses) purely because each thread just blocks on its own
`subprocess.run()` -- CPython releases the GIL for that wait, so this
genuinely runs multiple fits in parallel across CPU cores.

**Exact, not approximate**: `flim_fit_pixels_v2` fits every pixel fully
independently with no cross-pixel state, so chunking by rows and
concatenating the results back together is mathematically identical to
one whole-image call, just faster. This is also why it's deliberately
*not* offered for **FLIMLib — global shared τ** or **apply trained global
model**: those fit one τ jointly across every selected pixel by design --
chunking that would silently produce a different, wrong τ per chunk
instead of the one true whole-image joint fit. Those two methods keep
running single-process regardless of this setting.

### What's new

- `flim_app/native_backend.py`: new `fit_pixels_parallel_in_subprocess()`
  -- splits `decay`/a per-pixel `irf` into `worker_count` row-bands (a
  shared-trace or mismatched-shape IRF is instead handed to every chunk
  unchanged, exactly as the single-chunk path already does), fits each via
  the existing, untouched `fit_in_subprocess("pixels", ...)` from a
  `ThreadPoolExecutor`, and concatenates the per-pixel result arrays back
  along the row axis. `worker_count=1` (or an image with fewer rows than
  that) falls through to the original single-call path unchanged.
- `flim_app/models.py`: new `AnalysisSettings.native_fit_workers: int = 1`,
  clamped to `[1, 32]` in `normalized()`.
- `flim_app/processing.py`: the `flimlib_reconvolution` branch now calls
  `fit_pixels_parallel_in_subprocess(worker_count=cfg.native_fit_workers, ...)`
  instead of the plain single-process call; the global/apply-global
  branches are untouched.
- `flim_app/gui.py`: new sidebar field (labelled with this machine's own
  core count), wired into `_settings()`/`_apply_settings_to_ui()` --
  covered by the existing settings-preset `.ini` save/load (0.12.3) with
  no extra code, since that's driven generically off every
  `AnalysisSettings` field.

### Status

Implemented and reviewed via careful manual code tracing (no Python
interpreter available in this environment to actually benchmark it --
see `BUILDING.md`'s existing caveat). Please try a few worker counts on a
real multi-plane/large-image reconvolution fit, on a real multi-core
machine, and confirm: (a) results are numerically identical to
`worker_count=1` for the same dataset (they should be -- see "exact, not
approximate" above), and (b) wall-clock time actually drops with more
workers, up to roughly your core count.
