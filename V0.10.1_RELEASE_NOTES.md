# FLIM Studio 0.10.1

## Fixed: no multi-exponential decay curve was ever shown

The Multi-exponential tab already rendered per-component tau/amplitude
**maps**, but the Decay & fit plot (and the exported ROI decay curve) always
overlaid a mono-exponential "tail guide" line — regardless of whether a
bi- or tri-exponential native FLIMLib fit was actually run. There was no
view anywhere in the app showing the fitted decay curve for a bi/tri model.

- `analyse_roi` now reconstructs the native fitted curve for the selected
  region: for every successfully fitted pixel in the region it sums
  `background + IRF ⊛ Σ A_k·exp(-t/τ_k)` using that pixel's own fitted
  components, then convolves with the same IRF trace the native fit used.
  This is a display-only reconstruction (not read back from the DLL) and is
  labelled as such; it is not guaranteed bin-identical to FLIMLib's internal
  curve, and per-pixel-IRF fits use the mean IRF trace as an approximation.
- The Decay & fit tab (and Overview ROI decay panel) now plot this native
  reconvolution curve — labelled "Native Mono/Bi/Tri-exponential
  reconvolution" — whenever a native fit is available, in place of the old
  mono tail guide. The tail guide is still shown for non-native methods
  (Phasor, Mono-exponential fit, First moment), where no reconvolved curve
  exists.
- ROI export (`_analysis.npz`, `_decay.csv`, `_decay.png`) now includes this
  curve alongside the existing summed/mean decay and mono guide.

## Fixed: "Model order" silently doing nothing

"Model order" (mono/bi/tri) only ever takes effect for the two FLIMLib
native methods; for any other Lifetime method it was silently ignored, with
no indication in the UI. This is a very plausible cause of "bi/tri fitting
doesn't do anything," since the two controls live in different sidebar
sections and nothing coupled them.

- Changing "Model order" to bi/tri while the Lifetime method isn't one of
  the FLIMLib methods now shows an inline warning telling you to switch the
  method.

## Native fit transfer overhead

Every native (FLIMLib) fit runs in a disposable subprocess for crash
isolation, round-tripping the decay/IRF cubes through temporary `.npz`
files. Those files no longer use zlib compression (`native_backend.py`,
`native_worker.py`) — compressing/decompressing large float64 arrays cost
real CPU for a temp file that lives milliseconds and is never persisted.
This does not change a single fitted value; it only changes how the bytes
are packed on disk.

Two more aggressive versions of this optimization (shrinking the transfer
arrays to float32, and skipping the redundant full per-pixel IRF cube when
in Global IRF mode) were tried and reverted: the reference fixtures' "counts"
data turned out to be non-integer with a test asserting fitted output to
`1e-9`, and the IRF-cube change would have broken an existing test's
recorded shape contract. Neither could be safely verified without running
the test suite, so both were backed out rather than risking silent
numerical drift in a tool validated against LabVIEW to double precision.

## Timing diagnostics for the "LabVIEW feels faster" question

`native_backend.py`/`native_worker.py` now print a `NATIVE_WORKER_TIMING`
line to the console for every native fit, breaking wall-clock time into:
reading the transfer file, loading the DLL, the DLL fit call itself, and
writing results back — plus the parent's own npz-write and subprocess wall
time. Comparing the parent's `subprocess_wall_s` against the worker's own
`worker_total_s` isolates process-launch/interpreter-startup overhead
(where antivirus/EDR real-time scanning shows up, if present) from actual
fit compute time, since LabVIEW's in-process DLL call pays none of that
overhead. These are temporary diagnostic prints, not permanent UI.
