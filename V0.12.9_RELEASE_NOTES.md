# FLIM Studio 0.12.9

## "Max pixels": 0 now means no cap at all

Follow-up to 0.12.8's global-training pixel-budget fix, prompted by a
fair question: why cap the global/shared-τ fit's pixel count at all,
rather than always using every valid pixel?

**Answer, briefly:** it's a *performance* limit, not a correctness one.
Unlike per-pixel fitting (each pixel is independent, trivially cheap and
parallel), the global fit's coordinate-descent optimizer re-evaluates
its objective across *every selected pixel* on every trial of the shared
τ values — cost scales with pixel count × time bins × however many trial
evaluations the optimizer needs. Millions of pixels, uncapped, could
turn a training run into a very long one (or hit the subprocess's
timeout). The cap trades a little of that against speed.

But `AnalysisSettings.max_global_pixels` previously had a hard floor of
100 — there was no way to actually ask for "no cap," even though the
native DLL itself already fully supports exactly that: both
`flim_fit_global_pixels_v2` and `flim_train_global_model_v1`
(`native/flimfit_labview.c`) only apply the exclusion check when
`maxGlobalPixels > 0` in the first place. Typing `0` into the sidebar's
**Max pixels** field just got silently floored back up to 100 instead of
reaching the DLL as the "unlimited" value it was already designed to
understand.

### The fix

- `flim_app/models.py`: `AnalysisSettings.normalized()` now passes
  `max_global_pixels <= 0` through unchanged (as `0`) instead of flooring
  it to 100 — matching the DLL's own native convention exactly, no DLL
  change needed.
- 0.12.8's per-image fair-share pre-subsampling in
  `train_global_model()` already skipped itself whenever
  `max_global_pixels <= 0` (`if image_count > 1 and cfg.max_global_pixels
  > 0:`), so it required no further change — setting the cap to 0 now
  correctly means every valid pixel from every training image, with no
  subsampling at any level.
- Sidebar label updated to **"Max pixels (0 = all)"**, with a new
  explanatory note underneath.

The default stays `20,000`, unchanged — this is an available option, not
a new default, since removing the cap can genuinely make a large
multi-image training run much slower (or, for very large datasets,
risk the subprocess's own timeout). If you hit that, the previous
default (or something in between) is still there to fall back to.

### Status

Implemented and reviewed via careful manual code tracing, including
re-confirming the native DLL's own `maxGlobalPixels > 0` gate in
`native/flimfit_labview.c` for both entry points this setting reaches
(no Python interpreter available in this environment to run it — see
`BUILDING.md`'s existing caveat). Please set **Max pixels** to `0` on
your 3-image training set and confirm the **Px used/total** column now
shows each image's *full* pixel count (not just a capped share), and
that training still completes in reasonable time.
